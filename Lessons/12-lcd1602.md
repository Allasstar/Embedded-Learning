# Lesson 12: LCD 1602 Driver

## Goal
Write your own driver for the 16×2 character LCD and show live data on it: uptime and a counter of blue-button presses.

## What you learn
- Driving a parallel device through an **I/O expander** (PCF8574)
- Following a datasheet initialisation sequence
- 4-bit mode: sending a byte as two nibbles
- Enable strobes and timing
- Updating a display without flicker
- Mixing 5 V and 3.3 V devices: a separate I2C bus

## How it works
The LCD itself (HD44780 controller) has a **parallel** interface: RS (command/data), RW (read/write), EN (strobe), D0–D7. The blue board on its back (the "backpack") is a **PCF8574**: an I2C chip with 8 output pins. Writing one byte over I2C sets those 8 pins.

The backpack comes already soldered to the LCD's 16 pins, so you don't wire anything between them. The table below is the fixed wiring on the backpack's PCB. You need it in code, because each bit of the byte you send drives one LCD signal:

| PCF8574 bit | LCD signal |
|---|---|
| P0 | RS (0 = command, 1 = character) |
| P1 | RW (always 0 = write) |
| P2 | EN (LCD latches data on its falling edge) |
| P3 | Backlight |
| P4–P7 | D4–D7 |

Only 4 data lines are connected, so every byte is sent in **4-bit mode**: high nibble first, then low nibble, each latched by an EN pulse (HIGH then LOW).

### Which chip is on your backpack?
Read the marking on the chip:

| Marking | I2C address (A0–A2 pads open) |
|---|---|
| PCF8574**T** | **0x27** |
| PCF8574**AT** | **0x3F** |

The **T** only names the package (SO16), not the address. The **A** variant has a different fixed address range. Bridging the A0/A1/A2 solder pads on the backpack lowers the address. Leave them open.

## Parts and wiring
The only wiring is the backpack's 4-pin header (GND, VCC, SDA, SCL) to the board:

| LCD backpack pin | Board pin | Why |
|---|---|---|
| GND | GND | shared ground for the I2C signals |
| VCC | **5V** | the HD44780 and backlight need 5 V; at 3.3 V the text is faint or missing |
| SDA | PC9 | I2C3 data |
| SCL | PA8 | I2C3 clock |

**Why I2C3, not I2C1:** the backpack has its own pull-ups to VCC, so SDA and SCL idle at 5 V. I2C1 (PB6/PB9) is shared with the board's audio DAC and the 3.3 V modules, so they must not see 5 V. A separate bus keeps the 5 V levels on the LCD's lines only.

PA8 and PC9 are 5 V tolerant (FT), so the 5 V pull-ups are safe for the STM32.

## CubeMX setup
1. **Connectivity → I2C3**: mode *I2C*. Make sure the pins are **PA8 (SCL)** and **PC9 (SDA)**.
2. Speed Mode *Standard*, 100000 Hz. The PCF8574 is rated for 100 kHz only, so Fast mode (400 kHz) is out of spec.
3. Leave GPIO pull-ups off (*No pull-up and no pull-down*). The backpack already has pull-ups, and internal ones would pull to 3.3 V against them.
4. Generate.

First scan I2C3 by calling this from `App_Start()` (`#include "log.h"`). Expect **0x27** (PCF8574T) or **0x3F** (PCF8574AT).

```c
for (uint16_t address = 1; address < 128; address++)
{
  if (HAL_I2C_IsDeviceReady(&hi2c3, address << 1, 2, 5) == HAL_OK)
    LOG("found 0x%02X\n", address);
}
```

## Steps

### Step 1: Low-level writes

`Core/Inc/lcd.h`:

```c
#pragma once
#include <stdint.h>

void Lcd_Init(void);
void Lcd_Clear(void);
void Lcd_SetCursor(uint8_t row, uint8_t column);
void Lcd_Print(const char *text);
void Lcd_Printf(uint8_t row, const char *format, ...);
```

`Core/Src/lcd.c`:

```c
#include "lcd.h"
#include "main.h"
#include <stdarg.h>
#include <stdio.h>

extern I2C_HandleTypeDef hi2c3;

#define LCD_ADDR      (0x27 << 1)
#define LCD_RS        0x01
#define LCD_EN        0x04
#define LCD_BACKLIGHT 0x08

static void WriteNibble(uint8_t nibble, uint8_t rs)
{
  uint8_t data = (nibble << 4) | rs | LCD_BACKLIGHT;
  uint8_t sequence[2] = { data | LCD_EN, data };
  HAL_I2C_Master_Transmit(&hi2c3, LCD_ADDR, sequence, 2, 10);
}

static void WriteByte(uint8_t value, uint8_t rs)
{
  WriteNibble(value >> 4, rs);
  WriteNibble(value & 0x0F, rs);
}

static void Command(uint8_t command)
{
  WriteByte(command, 0);
}
```

Set `LCD_ADDR` to the address your scanner found (0x27 or 0x3F).

`sequence` sends the nibble with EN HIGH, then the same nibble with EN LOW. The falling edge latches it. One I2C byte takes ~90 µs at 100 kHz, much longer than the LCD's minimum pulse width (450 ns), so no extra delay is needed.

### Step 2: Initialisation
From the HD44780 datasheet, *"Initializing by instruction"*, 4-bit interface. After power-up the LCD might be in 8-bit mode, or halfway through a 4-bit transfer. Sending `0x3` three times forces it into a known 8-bit state; then `0x2` switches to 4-bit.

```c
void Lcd_Init(void)
{
  HAL_Delay(50);
  WriteNibble(0x03, 0);
  HAL_Delay(5);
  WriteNibble(0x03, 0);
  HAL_Delay(1);
  WriteNibble(0x03, 0);
  HAL_Delay(1);
  WriteNibble(0x02, 0);
  HAL_Delay(1);

  Command(0x28);
  Command(0x08);
  Lcd_Clear();
  Command(0x06);
  Command(0x0C);
}

void Lcd_Clear(void)
{
  Command(0x01);
  HAL_Delay(2);
}
```

| Command | Meaning |
|---|---|
| `0x28` | function set: 4-bit, 2 lines, 5×8 font |
| `0x08` | display off |
| `0x01` | clear (slow: 1.5 ms) |
| `0x06` | entry mode: cursor moves right after each character |
| `0x0C` | display on, cursor hidden |

Delays in `Init` are fine: it runs once at start-up.

### Step 3: Text

```c
void Lcd_SetCursor(uint8_t row, uint8_t column)
{
  Command(0x80 | ((row ? 0x40 : 0x00) + column));
}

void Lcd_Print(const char *text)
{
  while (*text)
    WriteByte((uint8_t)*text++, LCD_RS);
}
```

Line 2 starts at display memory address `0x40`, not 16. That's a quirk of the controller.

Test: `Lcd_Init(); Lcd_Print("Hello, world!");`

**Blank screen or a row of white boxes?** Turn the blue **contrast potentiometer** on the backpack with a small screwdriver. This is the most common "my code doesn't work" problem with these displays.

### Step 4: Printf to a line, no flicker

```c
void Lcd_Printf(uint8_t row, const char *format, ...)
{
  char buffer[17];
  char padded[17];
  va_list args;
  va_start(args, format);
  vsnprintf(buffer, sizeof(buffer), format, args);
  va_end(args);

  snprintf(padded, sizeof(padded), "%-16s", buffer);
  Lcd_SetCursor(row, 0);
  Lcd_Print(padded);
}
```

Calling `Lcd_Clear()` every update makes the screen flicker (blank, then redraw). Instead, overwrite each line padded with spaces to 16 characters: `%-16s` left-aligns and pads. Leftover characters from a longer previous text get overwritten.

### Step 5: Live dashboard
In a `Dashboard_Update()` that runs every 200 ms (`pressCount` is incremented in `App_Update()` on the blue button's rising edge, which `app.c` already detects):

```c
Lcd_Printf(0, "Up %lus", HAL_GetTick() / 1000);
Lcd_Printf(1, "Presses %lu", pressCount);
```

Updating faster than ~5 Hz is pointless: LCD crystals are slow and fast changes look smeared.

### Step 6: Measure the cost
Writing 32 characters = 64 nibbles = 64 I2C transfers ≈ **20 ms** of blocking I2C. Time `Dashboard_Update()` with `HAL_GetTick()`. That's why you don't redraw it 100 times a second.

## Troubleshooting
| Symptom | Cause |
|---|---|
| Backlight on, nothing visible | contrast pot |
| Top row of boxes | init failed: wrong address, or init sequence timing |
| Random characters | 4-bit mode lost sync: brownout or I2C error mid-byte, so re-run init |
| Not found by scanner | PA8/PC9 swapped, 5 V missing, or I2C3 on other pins in CubeMX |
| Backlight off | `LCD_BACKLIGHT` bit missing in a write, or backlight jumper removed |

## Challenges
1. **Custom characters**: the LCD has 8 user-defined 5×8 characters. Add `Lcd_CreateChar(index, pattern)`: send command `0x40 + index * 8`, then write the 8 pattern bytes as data (one byte per pixel row, bit 4 = leftmost pixel). Print the character by sending its code `index`.
   - Make a **degree symbol** and **5 bar pieces** (1 to 5 pixel columns filled, left to right).
   - Don't use slot 0. Code `0` is the C string terminator, so it can't go through `Lcd_Printf`. Use slots 1–5 for the bar and 6 for the degree sign.
   - After writing CGRAM, the LCD's address counter points into character memory, not the screen. Set the cursor before printing the next character.
2. **Bar graph**: draw a horizontal bar across all 16 columns with the bar pieces: 16 cells × 5 columns = **80 steps**. Drive it with uptime as a sawtooth that fills over 10 s and restarts. Cells left of the end are full (piece 5), the end cell is partial, and the rest are spaces.
3. **Non-blocking updates**: a full redraw blocks for ~20 ms (Step 6). Make `Lcd_Printf` only write into a 32-char **desired** buffer, with no I2C. Add `Lcd_Update()`, called on every pass of `App_Update()`. It compares desired with a **shown** buffer and sends **at most one** changed character (~1 ms).
   - Remember where the LCD's cursor is. It advances by itself after each character, so a run of changed neighbours needs only one cursor command.
   - After column 15 the cursor moves to address `0x10`, which is off-screen, not to line 2. Treat it as unknown there.
   - Make `Lcd_SetCursor`/`Lcd_Print` private, because direct writes would make the shown buffer wrong. `Lcd_Clear` resets both buffers to spaces.
   - Since writes are now cheap, refresh the dashboard every 50 ms, so the bar moves one step (125 ms) at a time instead of jumping.
4. **Real temperature for the degree symbol**: the STM32 has a built-in temperature sensor on ADC1 channel 16. Show it on row 0 as e.g. `123s P3 38°C`, read once a second.
   - Set up ADC1 directly with registers in `temp_sensor.c`. That way, regenerating CubeMX never overwrites it.
     - Enable the ADC1 clock.
     - In `ADC123_COMMON->CCR`, set prescaler /4 (84 MHz / 4 = 21 MHz, under the 36 MHz maximum) and `TSVREFE`, which turns the sensor and VREFINT on.
     - Set the sample time to 480 cycles for channels 16 and 17 (23 µs; the datasheet needs at least 10 µs).
     - Set `ADON`, then wait 1 ms for start-up.
   - Average 16 samples, because the sensor is noisy.
   - Convert with the factory calibration stored in system memory: `TS_CAL1` (0x1FFF7A2C, raw at 30 °C) and `TS_CAL2` (0x1FFF7A2E, raw at 110 °C). Draw a straight line between the two points.
   - The calibration was measured at VDDA = 3.3 V, but the Discovery runs at **3.0 V**. Also read VREFINT (channel 17, a fixed 1.21 V) and scale the reading by `VREFINT_CAL / vrefint` (0x1FFF7A2A) to correct for this.
   - The sensor measures the **die** temperature, typically 5–15 °C above the room. Touch the chip and watch the value rise.
